# Model API 延迟监控设计

## 背景

插件当前通过 Manifest V3 Service Worker 调用 OpenAI-compatible Chat Completions API，并在 Popup 中提供控制、Token 监控和运行日志。现有请求流程已经具有请求发起、响应头返回、流式首个译文片段以及响应完成等时间节点，但尚未记录 API 延迟。

本次增加独立的延迟监控，用于观察不同 API 服务、模型和响应模式下的实际用户等待时间。统计只反映浏览器端观测到的网络、网关排队和模型生成总时间，不宣称等同于服务端纯模型推理耗时。

## 目标

- Popup 调整为“控制 / Token / 延迟 / 日志”四个标签页。
- 统计 TTFB、流式 TTFT 和请求总耗时。
- 展示历史延迟、今日请求结果、不同 API Host、模型及响应模式的延迟情况。
- 保存最近 90 天每日聚合和最近 500 次成功请求样本。
- 统计成功、失败、超时和取消次数，不把失败请求混入成功延迟分布。
- 延迟数据与现有 Token 统计、日志和配置相互独立。
- 不保存完整 Base URL、请求内容、译文、Token 或响应体。

## 非目标

- 不测量或推断服务端纯模型推理耗时。
- 不依赖非标准的 `Server-Timing` 响应头。
- 不记录单次失败请求的详细耗时。
- 不提供费用与延迟关联分析、数据导出或远程上报。
- 不保存最近 90 天内的全部请求明细。
- 不修改翻译提示词、选区规则、请求超时和现有错误语义。
- 不新增配置项、第三方图表库或单元测试。

## 指标定义

所有耗时均在 Service Worker 中使用 `performance.now()` 计算并四舍五入为非负整数毫秒，避免系统时间调整影响持续时间。

### TTFB

从调用 `fetch()` 前到 `fetch()` 返回响应头的耗时。它包括浏览器网络处理、连接建立、服务端排队以及服务端生成首个响应字节前的时间。

只有最终成功的翻译请求进入 TTFB 聚合与分位数。HTTP 错误虽然能获得响应头，但只累计失败次数，不进入成功延迟统计。

### TTFT

从调用 `fetch()` 前到解析出第一个非空 `choices[0].delta.content` 的耗时。

- 仅流式成功请求具有 TTFT。
- SSE 元数据、空内容和 usage 事件不视为首个译文片段。
- 非流式请求无法从完整 JSON 响应中得到真实首字时间，界面显示 `--`，不以 TTFB 或总耗时代替。

### 总耗时

- 流式响应：从调用 `fetch()` 前到收到 `data: [DONE]` 并确认已经产生有效译文。
- 非流式响应：从调用 `fetch()` 前到读取完整 JSON 并确认译文有效。

Token 与日志的本地存储时间不计入总耗时。只有最终成功的翻译请求进入总耗时统计。

## 请求结果分类

仅在即将调用 `fetch()` 时开始一次延迟监控请求。配置缺失、Base URL 无效和配置读取失败没有实际发起 API 请求，因此不计入延迟统计，仍沿用现有运行日志记录。

API 请求结果分为：

- `success`：获得有效译文并按响应模式正常完成；记录完整成功延迟。
- `failure`：网络错误、HTTP 错误、无效响应、无效流或流异常中断；只累计次数。
- `timeout`：由现有 30 秒超时中止；只累计次数。
- `canceled`：用户关闭浮层、产生新选区、关闭翻译或页面离开导致请求中止；只累计次数。

失败、超时和取消不进入平均值、最小值、最大值、P50 或 P95。已经取得部分流式译文但未收到 `[DONE]` 的请求仍按失败、超时或取消分类，不计为成功。

## 统计维度

每次请求按以下三项组成目标维度：

```text
API Host + Model + 响应模式
```

- `API Host` 使用已校验 Base URL 的 `URL.host`，包含非默认端口但不包含协议、路径、查询或片段。
- `Model` 使用发起请求时的配置值。
- 响应模式为 `stream` 或 `non-stream`。

相同 Host、Model 和响应模式合并统计。任一项不同则作为不同目标，避免不同服务商或流式模式的数据互相污染。

## 本地数据模型

新增独立的 `latencyMetrics` 键：

```js
latencyMetrics: {
  total: {
    successCount: 0,
    failureCount: 0,
    timeoutCount: 0,
    canceledCount: 0,
    ttfb: { count: 0, totalMs: 0, minMs: 0, maxMs: 0 },
    ttft: { count: 0, totalMs: 0, minMs: 0, maxMs: 0 },
    duration: { count: 0, totalMs: 0, minMs: 0, maxMs: 0 }
  },
  byTarget: {
    "<内部目标键>": {
      host: "api.example.com",
      model: "model-name",
      streamEnabled: true,
      // 与 total 相同的计数和耗时聚合
    }
  },
  byDate: {
    "YYYY-MM-DD": {
      // 与 total 相同的计数和耗时聚合
    }
  },
  samples: [
    {
      timestamp: 1788315000000,
      targetKey: "<内部目标键>",
      ttfbMs: 420,
      ttftMs: 680,
      durationMs: 1350
    }
  ]
}
```

- `total` 长期保存全部请求结果计数及成功耗时聚合。
- `byTarget` 长期按目标维度保存相同聚合。
- `byDate` 按浏览器本地日期保存最近 90 个自然日的相同聚合。
- `samples` 全局最多保存最近 500 次成功请求，用于计算整体及各目标维度的近期 P50/P95。
- 非流式样本的 `ttftMs` 为 `null`，不会进入 TTFT 分位数。
- `timestamp` 使用 `Date.now()`，只用于样本保留顺序；持续时间仍使用 `performance.now()`。
- 内部目标键由 Host、Model 和响应模式确定，界面展示独立保存的字段，不向用户展示编码后的键。

## 聚合与分位数

长期平均值通过 `totalMs / count` 计算。首次写入某个耗时指标时，最小值和最大值均设为本次值；后续分别更新最小值和最大值。

P50 与 P95 只基于最近 500 次成功样本：

1. 按当前展示范围筛选样本；
2. 取出对应耗时并升序排列；
3. 使用 nearest-rank 规则，索引为 `ceil(p * n) - 1`；
4. 没有对应样本时显示 `--`。

由于样本是全局最近 500 次成功请求，低频目标如果在最近 500 次中没有样本，其长期平均值和请求数仍会保留，但 P50/P95 显示 `--`。

## 数据采集流程

```text
配置读取与校验
       |
       v
记录 requestStart = performance.now()
       |
       v
调用 fetch()
       |
       +-- 返回响应头 --------> 记录 TTFB
       |
       +-- 流式首个非空内容 -> 记录 TTFT
       |
       +-- 有效响应完成 ------> 记录成功及总耗时
       |
       +-- 请求异常 ----------> 记录 failure / timeout / canceled
                                  |
                                  v
                          串行存储队列
                                  |
                     latencyMetrics / tokenUsage / runtimeLogs
```

现有 `translate` 调用者继续接收成功模型或错误，Content Script 的 `chunk`、`done`、`error` Port 协议不变。延迟记录是旁路副作用，不能改变译文发送、Token 统计或用户错误提示。

为保证分类准确，`translate` 在请求开始后保留目标维度和计时状态，并在唯一出口记录一次结果：

- 成功路径在响应校验完成后记录一次 `success`。
- 捕获异常后在重新抛出前记录一次对应失败类别。
- 请求开始前的配置类错误不记录延迟结果。
- 同一请求不得重复累计结果。

## 串行存储与保留策略

延迟累计和延迟重置进入现有 Service Worker 存储修改队列，与 Token 累计、日志追加、Token 重置和日志清空按入队顺序执行。

- 每次写入从 `chrome.storage.local` 读取最新 `latencyMetrics`，完成一次原子式读改写。
- `byDate` 删除当天及此前 89 个本地自然日之外的数据。
- 成功样本追加后只保留最后 500 条。
- Service Worker 重启后内存队列从空状态开始，已经写入的数据不受影响。
- 延迟写入失败只输出控制台错误并沿用现有脱敏运行日志能力，不把已经成功的翻译改成失败。

重置延迟统计通过 Service Worker 消息进入同一队列并删除 `latencyMetrics`：

- 重置之前已经排队完成的数据被清除。
- 重置之后才进入队列的请求结果作为新统计保留。
- 重置不影响 `tokenUsage`、`runtimeLogs` 或任何插件配置。

## Popup 交互

Popup 顶部标签调整为：

```text
控制 | Token | 延迟 | 日志
```

原“监控”标签改名为“Token”，内容和行为保持不变。新增“延迟”标签包含：

### 历史概览

- 成功请求总数；
- 平均总耗时；
- 最近样本 P50；
- 最近样本 P95。

### 今日请求结果

- 成功次数；
- 失败次数；
- 超时次数；
- 取消次数。

### 按目标统计

按历史成功请求数降序展示，每项包含：

- API Host；
- Model；
- 流式或非流式；
- 成功、失败、超时和取消次数；
- 平均 TTFB；
- 平均 TTFT，非流式显示 `--`；
- 平均总耗时；
- 最近样本 P50/P95。

### 最近 90 天

按日期倒序展示：

- 成功、失败、超时和取消次数；
- 当日成功请求的平均 TTFB；
- 当日流式成功请求的平均 TTFT；
- 当日成功请求的平均总耗时。

没有延迟数据时，各区域显示空状态。Popup 打开期间监听 `latencyMetrics` 变化并实时刷新。

“重置延迟统计”使用危险操作样式和确认弹窗：

> 将永久清除历史延迟、目标统计、每日统计和最近样本，此操作不会清除 Token 统计或日志，是否继续？

用户取消时不发送重置命令；重置失败时保留当前数据并显示错误。

## 隐私与日志

延迟统计只保存 API Host、Model、响应模式、计数和耗时。禁止保存：

- Base URL 协议、路径、查询和片段；
- API Token 或其他请求头；
- 用户选择的原文和翻译结果；
- 请求体、响应体和原始异常对象。

延迟统计写入或重置失败沿用固定事件映射写入运行日志。日志仍不得接收调用方提供的任意正文。

## 兼容性

- 新增 `latencyMetrics` 键，不修改现有配置、`tokenUsage` 和 `runtimeLogs` 数据结构。
- 升级后不存在延迟数据时按空数据处理，无需迁移。
- 不修改 OpenAI-compatible 请求字段、SSE 解析协议、超时规则和 Content Script Port 协议。
- 用户现有 Base URL、Token、Model、流式开关和自动翻译开关全部保留。

## 验证计划

### 静态检查

- 对所有修改的 JavaScript 文件执行 `node --check`。
- 验证 `manifest.json` 可正常解析。
- 执行 `git diff --check`。
- 项目没有 Makefile，因此不执行 make 目标。
- 不新增单元测试，不执行 lint 或 test。

### 数据与请求路径

- 非流式成功请求正确记录 TTFB 和总耗时，TTFT 保持为空。
- 流式成功请求在首个非空译文片段记录 TTFT，在 `[DONE]` 记录总耗时。
- SSE 元数据、空内容和 usage 不触发 TTFT。
- 网络错误、HTTP 错误、无效响应、无效流和流中断只累计失败次数。
- 超时和用户取消分别累计，不进入成功延迟。
- 配置类错误不进入延迟统计。
- 同一请求只记录一个最终结果。
- 不同 Host、Model 或响应模式正确分组。
- 并发完成时统计不丢失。
- 最近 90 天每日数据和最近 500 次成功样本正确裁剪。
- P50/P95符合 nearest-rank 规则。
- 延迟重置不影响 Token 和日志。

### Chrome 验证

- 四个标签可正常切换，原控制、Token 和日志页面无回归。
- 延迟历史概览、今日结果、目标列表、每日列表和空状态正确展示。
- `latencyMetrics` 更新后 Popup 实时刷新。
- 重置确认、取消、成功和失败行为符合设计。
- 页面与扩展控制台没有新增 JavaScript 错误。

真实流式和非流式延迟端到端验证依赖用户配置的 OpenAI-compatible 服务。没有使用真实 API 配置时，只能验证计时节点、聚合逻辑、失败分类、存储行为和 Popup 展示，不能声称完成真实 API 延迟端到端验证。

## 完成标准

- Popup 提供独立延迟标签，并保持现有功能兼容。
- 成功请求的 TTFB、流式 TTFT 和总耗时按定义采集。
- 失败、超时和取消只累计结果次数，不污染成功延迟。
- 历史、目标维度、最近 90 天和最近 500 次样本满足保留规则。
- P50/P95仅依据最近成功样本计算。
- 延迟重置不影响 Token、日志和配置。
- 本地数据满足脱敏要求。
- 所有可执行静态检查和 Chrome 验证完成，未完成的真实 API 验证被明确说明。
